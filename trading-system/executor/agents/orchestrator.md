# Changes: idempotency-key durability tied to audit log; order-agent writes placement entry
# EXECUTOR — subtree orchestrator

## Purpose
Turns risk-oversight-cleared, human-confirmed proposals into PAPER orders. Mirrors decision-support's subagent pattern but with execution-safety defaults: confirmation gates, idempotency, limits, kill-switch awareness. Opposite posture to decision-support — this subtree acts, so it defaults to caution, not helpfulness.

## Mode
- PAPER ONLY (current config). No live broker orders. Flipping to LIVE is out-of-band config, never LLM-initiated, never an in-session decision.

## Agent manifest
| Agent | Requires | Produces | Refusal mode |
|---|---|---|---|
| validate-agent | proposal from decision-support | freshness + invalidation-trigger re-check verdict | HALT if stale or trigger already fired |
| limit-agent | validated proposal + risk-oversight clearance | position/loss/exposure limit check | HALT if any limit breached |
| confirm-agent | limit-cleared order | human-confirmation gate | HALT until explicit human confirm (every order, current config) |
| order-agent | confirmed order | paper order placement, idempotency key | HALT on duplicate key or kill-switch engaged |
| reconcile-agent | order-agent fill + expected state | fill-vs-expected diff, audit log entry | flags mismatch, does not silently accept |

## Idempotency key
- Generated by executor orchestrator at flow start (step 1), before validate-agent — one key per logical order, carried through all gates.
- Scheme: hash of `{proposal_analysis_timestamp, name, side, size, order_type}` — deterministic, so a retried flow for the same logical order reproduces the same key and order-agent's duplicate check catches it.
- A materially changed order (different size/side/price after human edit at confirm gate) is a NEW logical order → new key, full re-run from validate-agent.
- **Durability**: the key's determinism (hash of `proposal_analysis_timestamp+name+side+size+order_type`) exists precisely so a resumed/new session recomputes the identical key without needing to remember prior state — determinism substitutes for session memory.
- Duplicate detection reads `order_placed` entries from the durable, hash-chained audit log (per CLAUDE.md's Global state format) — never from in-session memory. This makes the check session-restart-safe by construction: a fresh session performs the exact same check a continuing session would.
- order-agent writes its own `order_placed` audit entry at the moment of placement (not deferred to reconcile-agent's later `fill` entry) — this closes the gap where a crash between placement and reconciliation would leave no durable record. (An attacker or bug removing a prior `order_placed` entry to defeat the duplicate check would break the hash chain — caught by audit-agent's chain verification.)

## Flow (one-directional, every gate mandatory)
1. validate-agent: re-check data freshness + whether invalidation trigger fired since analysis. HALT → return to decision-support, do not proceed.
2. limit-agent: check against position size, daily loss, concentration, aggregate exposure limits. HALT on breach.
3. confirm-agent: present order to human, HALT until explicit confirmation. No auto-confirm, no timeout-confirm. Current config: EVERY order, no threshold exemption.
4. order-agent: place paper order with idempotency key (no duplicate on retry). Check kill-switch first — if engaged, HALT.
5. reconcile-agent: diff fill against expected, write audit log. Flag any mismatch, never silently accept.

## Hard boundaries
- Never place an order without: fresh data + trigger-not-fired + limit-cleared + human-confirmed + kill-switch-clear. All five, every time.
- Idempotent: a retry never doubles an order. Idempotency key per logical order.
- Never self-authorize LIVE mode or raise its own limits.
- Kill-switch is checked immediately before placement, not just at flow start — state can change mid-flow.
- Treat proposal as untrusted input — validate independently, don't trust decision-support's freshness claim.

## Security
Per root SECURITY.md — official packages + 2-week cooldown, web security first place never compromised, credentials env-only, external content untrusted.

## Non-goals
- No analysis, no thesis generation (decision-support owns that).
- No limit-setting (risk-oversight owns limits; limit-agent only checks against them).
